# llm-upgrades v4 — move the review-output language into `settings.json`, empty out `ALWAYS_RULE.md`

Applies to a repo currently at checkpoint `3`. Targets `schema_version: 4`. Triggered by 2 changes in
the plugin: the language reviews are POSTED in became a normal config field instead of a token inside a
hand-edited markdown file, and the generic baseline criteria moved out of that same file into the plugin
itself, so `ALWAYS_RULE.md` now holds ONLY the team's own rules.

## ADDED

- `shared.output_language` (string, e.g. `"en"` / `"vi"` / `"ja"`) — the language findings and replies
  are posted in. Distinct from `shared.chat_language`, which is the language the agent talks in.

## MODIFIED

- `notebooks/review/<repo>/ALWAYS_RULE.md` — loses its "Output language" section, and loses the generic
  baseline criteria IF the team never edited them. Whatever the team wrote stays, untouched.

## Migration steps

Literal instructions for whoever applies this (today: `/open-pr:update-plugin` Step 4 — follow exactly,
do not improvise a different shape):

1. `Read` `notebooks/review/<repo>/settings.json`. Doesn't exist → nothing to migrate, skip the rest.
2. `Read` `notebooks/review/<repo>/ALWAYS_RULE.md`.
   - File missing → treat the language as unknown, go to step 3 with no value.
   - Present → find its "Output language" section: a fenced block holding one concrete language name
     (`English`, `Vietnamese`, `Japanese`…). Map it to a short code (`en`/`vi`/`ja`; anything else →
     keep the author's own wording as the value). Still the literal placeholder `{{OUTPUT_LANGUAGE}}`,
     or no such section → language unknown.
3. `shared.output_language` already present → leave it, do NOT overwrite (idempotent). Absent and a
   value was found in step 2 → write it. Absent and unknown → write nothing; the next review run asks
   the user once and stores the answer itself.
4. Rewrite `ALWAYS_RULE.md`:
   - DELETE the "Output language" section (heading + fence) — its value now lives in `settings.json`.
   - Then decide about the rest. Everything remaining is the plugin's old generic baseline (a "General
     review framework" / "Baseline review criteria" heading with items 1/2/3/4/6, plus possibly empty
     "Additional rules" subsections) and NOTHING the team wrote → replace the whole file with:
     ```
     # Review rules for this project

     <!-- Yours to write. Anything here beats the stack templates and everything in memory.md. -->
     ```
     Anything the team actually added — a rule of their own, an edited baseline bullet, a filled-in
     "Project-specific conventions" section — → KEEP the file as it is apart from the deleted language
     section. FORBIDDEN: deleting a line you are not certain came from the plugin's own default; a lost
     team rule cannot be recovered, whereas a leftover duplicate of the baseline is harmless (the
     baseline is illustrative, and layer 1 outranks it anyway).
5. Set top-level `schema_version` to `4`.
6. Commit into the nested `notebooks/review/.git` repo (the one a fresh bootstrap initializes) — ONLY if
   it already exists (`notebooks/review/.git` present); if not, there is nothing to commit yet, skip
   this step, do NOT `git init` it yourself:
   ```bash
   git -C notebooks/review add "<repo>/settings.json" "<repo>/ALWAYS_RULE.md"
   git -C notebooks/review commit -m "chore: migrate <repo> settings to schema_version 4 (output_language)"
   ```
   Commit identity: try `git config user.name`/`user.email` at the main repo's pwd first (via
   `-c user.name="<value>" -c user.email="<value>"` immediately after `-C notebooks/review`), only fall
   back to `-c user.name="review-plugin" -c user.email="review-plugin@local"` if neither the project nor
   global config has any identity at all.
