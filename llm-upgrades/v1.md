# llm-upgrades v1 — the pre-`schema_version` config becomes `settings.json`

Applies to any repo bootstrapped before this plugin had a `schema_version` at all: 2 separate files,
`notebooks/review/<repo>/meta.json` for `review.md` and `notebooks/review/<repo>/fix-meta.json` for
`fix.md`, with `chat_language` written independently into both. Targets `schema_version: 1` — the first
and, so far, only migration.

## RENAMED

- `meta.json` + `fix-meta.json` → one `settings.json`, restructured into 3 nodes: `shared`, `review`,
  `fix`. Each command owning exactly one node is what makes the old dual-write of `chat_language`
  impossible rather than merely fixed.

## ADDED

- top-level `schema_version` (number) → `1`
- `shared.chat_language` — the ONE place it lives from now on
- `shared.git_remote_type` (`"github"` | `"gitlab"`) → `"github"`: every repo predating this migration
  was reviewed on the plugin's only vendor at the time, so this is a fact about old data, not a guess
- `shared.output_language` — the language findings and replies are POSTED in, distinct from
  `chat_language`, the language the agent TALKS in. Recovered from `ALWAYS_RULE.md`, see step 5

## MODIFIED

- `ALWAYS_RULE.md` loses its "Output language" section, and loses the plugin's generic baseline criteria
  IF the team never edited them. Whatever the team wrote stays untouched.

## REMOVED

- `meta.json` and `fix-meta.json`, once merged

## Migration steps

Literal instructions for whoever applies this — today `/open-pr:upgrade` Step 5. Follow exactly;
do not improvise a different shape.

1. `Read` `meta.json` and `fix-meta.json` under `notebooks/review/<repo>/`, each as `{}` when absent.
   Neither exists → `Write` `{"schema_version": 1}` and stop; this repo never bootstrapped either
   command.
2. `chat_language`: `meta.json`'s value, else `fix-meta.json`'s, else omit `shared.chat_language`
   entirely. BOTH present and disagreeing — the bug-class this migration removes — → take `meta.json`'s
   (reviews run more often than fixes, so it is the value the user last saw) and say so plainly in Step
   5's summary.
3. `review` node ← every key of `meta.json` except `chat_language`, names and values unchanged.
   `meta.json` absent → omit the node.
4. `fix` node ← every key of `fix-meta.json` except `chat_language`, unchanged. Absent → omit the node.
5. `output_language`: `Read` `ALWAYS_RULE.md`. Its "Output language" section is a fenced block holding
   one language name → map to a short code (`en`/`vi`/`ja`; anything else → keep the author's own
   wording). Still the literal `{{OUTPUT_LANGUAGE}}`, no such section, or no file → unknown, write
   nothing: the next review asks once and stores the answer itself.
6. `Write` `settings.json`:
   ```json
   {
     "schema_version": 1,
     "shared": { "chat_language": "<step 2>", "output_language": "<step 5>", "git_remote_type": "github" },
     "review": { "...": "step 3" },
     "fix": { "...": "step 4" }
   }
   ```
   Omit `shared`/`review`/`fix` and any `shared` key per the rules above. A key already present keeps
   its value — this migration is idempotent and never downgrades a correct `"gitlab"` to `"github"`.
7. Delete `meta.json` and `fix-meta.json`, whichever existed.
8. Rewrite `ALWAYS_RULE.md`: DELETE the "Output language" heading and its fence. Then, if EVERYTHING
   remaining is the plugin's old default — a "General review framework" or "Baseline review criteria"
   heading with items 1/2/3/4/6, plus possibly empty "Additional rules" subsections — and the team wrote
   nothing of their own, replace the whole file with:
   ```
   # Review rules for this project

   <!-- Yours to write. Anything here beats the stack templates and everything in memory.md. -->
   ```
   Anything the team did add — their own rule, an edited baseline bullet, a filled-in section — → keep
   the file as-is apart from the deleted language section. FORBIDDEN: deleting a line you are not
   certain came from the plugin's default. A lost team rule is unrecoverable; a leftover copy of the
   baseline is harmless, since the baseline is illustrative and the team's file outranks it anyway.
9. Commit into `notebooks/review/.git` — ONLY if it already exists; absent means nothing to commit yet,
   so skip, and FORBIDDEN: `git init` here.
   ```bash
   git -C notebooks/review add "<repo>/settings.json" "<repo>/ALWAYS_RULE.md"
   git -C notebooks/review rm --cached "<repo>/meta.json" "<repo>/fix-meta.json" 2>/dev/null
   git -C notebooks/review commit -m "chore: migrate <repo> config to schema_version 1"
   ```
   `rm --cached` may error harmlessly when a file was never tracked — ignore it. Commit identity: try
   `git config user.name`/`user.email` at pwd first, passing them as `-c user.name="<v>" -c
   user.email="<v>"` immediately after `-C notebooks/review`; only if neither project nor global config
   has any identity, fall back to `-c user.name="review-plugin" -c user.email="review-plugin@local"`.
